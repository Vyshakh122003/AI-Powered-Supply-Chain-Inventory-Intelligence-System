## 1. The Problem & Our Solution

**Problem:** Small Indian retail (kirana) stores manage 200–2000 SKUs manually. They have no data-driven way to know *when* a product will run out, *how much* to reorder, or *which supplier* gives the best value. This leads to frequent stockouts (lost sales) and overstocking (dead capital).

**Our Solution — StockSense AI:**
A web-based inventory intelligence system that:
- **Predicts** when each product will go out of stock (days-to-stockout projection)
- **Classifies** products into risk tiers (HIGH / MEDIUM / LOW / OOS)
- **Generates AI-powered reorder recommendations** using an LLM that considers supplier reliability, pricing, and delivery speed
- **Sends WhatsApp alerts** to the store owner about critical items
- **Tracks inventory health** over time with a daily health score

The entire pipeline runs automatically every day at 8 AM, or on-demand via a single button click.

| Technology | Where Used | Why Chosen |
|---|---|---|
| **Supabase** | Database, Auth, Realtime | Open-source Firebase alternative built on PostgreSQL. Provides: (1) Managed Postgres with a REST API — no backend needed for CRUD. ### Why This Architecture? (The "No Traditional Backend" Philosophy)

Traditional apps have: `Frontend → REST API (Express/Django) → Database`

Our approach: `Frontend → Supabase (direct DB access) + n8n (async workflows)`

**Why?**
- **Supabase replaces the CRUD API layer** — the React frontend calls Supabase directly for all reads/writes. No Express server, no Django, no API boilerplate.
- **n8n replaces the business logic layer** — all complex computations (risk classification, stockout calculation, AI recommendations) run as visual workflows triggered by webhooks or schedules.
- **Result:** Zero server-side code to maintain. The entire "backend" is configuration (n8n JSON exports + Supabase schema).

### The 8 Tables — Quick Reference

| # | Table | Purpose | Updated By |
|---|---|---|---|
| 1 | **Store Profiles** | One row per registered store (owner info, WhatsApp numbers, safety factor) | Signup, Onboarding, Settings |
| 2 | **Products** | Master product catalog — stock levels, sales velocity, risk classification, stockout projections | WF-01 (ingest), WF-02 (stockout), WF-04 (risk), WF-08 (simulation) |
| 3 | **Suppliers** | Supplier directory with multi-criteria scoring (reliability, price, delivery speed) | Manual + WF-06 (scoring) |
| 4 | **Stock Alerts** | Low stock alerts when `current_stock ≤ reorder_threshold` | WF-03 (full refresh each pipeline run) |
| 5 | **Reorder Suggestions** | AI-generated reorder recommendations with supplier matching and quantity | WF-05 (AI via Groq/Llama) |
| 6 | **Stock Transactions** | Immutable audit ledger of all stock changes (sales, restocks, adjustments) | WF-08 (daily depletion), Quick Update page |
| 7 | **Daily Snapshots** | Daily health score snapshots powering the trend chart | WF-08 (end of pipeline) |
| 8 | **System Logs** | Workflow execution logs for monitoring and debugging | Every workflow logs its status here |

### Supabase Realtime

These tables have **Realtime enabled** so the frontend updates instantly without page refresh:
- Products, Stock Alerts, Reorder Suggestions, Daily Snapshots, Suppliers

**How it works:** When n8n updates a row in the `Products` table, Supabase broadcasts the change over WebSocket → React's `useEffect` subscription fires → `fetchData()` re-runs → UI updates in real-time.

## 5. Backend Layer — n8n Workflow Engine

### What is n8n?

n8n is a **visual workflow automation platform** (self-hosted). Think of it as "Zapier but you host it yourself." Each workflow is a chain of nodes (Supabase queries, code blocks, HTTP requests, IF conditions) connected visually. The workflows are exported as JSON files stored in `backend/`.

### The 8 Workflows — Detailed Breakdown

---

#### WF-01: Product & Sales Data Ingestion

```
  Frontend POST                  n8n Workflow
  ─────────────                  ────────────
  AddProductModal    ──POST──►  Webhook: /product-sales-ingest
  CsvImportModal                       │
                                       ▼
                              Clean & Normalize Fields
                              (trim strings, parse numbers)
                                       │
                                       ▼
                              Check: product_id exists?
                                  /          \
                                YES           NO
                                /              \
                             UPDATE          INSERT
                           (upsert)       (new product)
                                \              /
                                 \            /
                                  ▼          ▼
                              Return { action: 'updated' | 'created' }
```

**Trigger:** POST webhook `/product-sales-ingest`
**Called by:** React frontend (AddProductModal, CsvImportModal)
**Purpose:** Receives product/sales data, cleans it, and upserts into the Products table.

---

#### WF-02: Stockout Date Calculator

```
  Supabase                    Calculation
  ────────                    ───────────
  Fetch ALL Products  ──►  For each product:
                              │
                              ├─ If avg_daily_sales = 0 → days_to_stockout = 999
                              ├─ If current_stock = 0   → days_to_stockout = 0
                              └─ Otherwise → floor(current_stock / avg_daily_sales)
                              │
                              ▼
                           estimated_stockout_date = today + days_to_stockout
                              │
                              ▼
                           UPDATE Products SET days_to_stockout, estimated_stockout_date
```

**Trigger:** Sub-workflow call from WF-08
**Purpose:** Projects when each product will run out of stock.

---

#### WF-03: Inventory Processing & Stock Alerts

```
  Supabase                    Alert Generation
  ────────                    ────────────────
  Fetch ALL Products  ──►  Filter: current_stock ≤ reorder_threshold
                              │
                              ▼
                           DELETE all existing Stock Alerts (full refresh)
                              │
                              ▼
                           INSERT new alerts for each low-stock product
                           (alert_name, current_stock, threshold, date)
```

**Strategy:** Full-refresh (delete-and-recreate). This ensures alerts always reflect the *current* state. No stale alerts persist.

---

#### WF-04: Stock Risk Classification

```
  Supabase                    Classification Rules
  ────────                    ────────────────────
  Fetch ALL Products  ──►  For each product:
                              │
                              ├─ days_to_stockout ≤ 3  → risk_level = 'HIGH'
                              ├─ days_to_stockout 4–7   → risk_level = 'MEDIUM'
                              ├─ days_to_stockout > 7   → risk_level = 'LOW'
                              └─ No data                → risk_level = 'UNKNOWN'
                              │
                              ▼
                           UPDATE Products SET risk_level
```

**Depends on:** WF-02 (needs `days_to_stockout` calculated first)

**Note (Frontend OOS Override):** In the React UI, the `RiskBadge` component has an additional rule: if `current_stock = 0`, it always displays **OOS** regardless of the database `risk_level`. This gives clearer visual feedback for completely empty stock.

#### WF-05: AI Reorder Intelligence ⭐ (The AI Core)

```
  Supabase                           Groq LLM API
  ────────                           ─────────────
  Fetch at-risk products     ──►  Build AI Prompt:
  (HIGH/MEDIUM/UNKNOWN)              "You are an inventory analyst.
  +                                   Here are products at risk: [...]
  Fetch ALL suppliers                 Here are available suppliers: [...]
                                      Recommend quantities and suppliers."
                                           │
                                           ▼
                                    POST to Groq API
                                    (Llama 3.1 8B Instant)
                                           │
                                           ▼
                                    Parse JSON response into rows:
                                    { product_id, supplier_id,
                                      suggested_quantity, reason }
                                           │
                                           ▼
                              DELETE old Reorder Suggestions
                                           │
                                           ▼
                              INSERT fresh AI recommendations
```

**AI Model:** Groq — Llama 3.1 8B Instant
**Why Groq?** Fastest inference (~100ms), free tier, runs Meta's open-source Llama model.
**What the AI considers:** Current stock, avg daily sales, days to stockout, supplier reliability scores, price competitiveness, delivery speed, store's safety factor.

#### WF-06: Supplier Scoring

```
  Supabase                    Weighted Sum Model (WSM)
  ────────                    ──────────────────────────
  Fetch ALL Suppliers  ──►  For each supplier:
                              │
                              ├─ Reliability Score × 0.40 (40% weight)
                              ├─ Price Score       × 0.35 (35% weight)
                              └─ Delivery Speed    × 0.25 (25% weight, min-max normalized)
                              │
                              ▼
                           composite_score = weighted sum × 100 (0–100 scale)
                              │
                              ▼
                           Assign grade:
                              ├─ ≥ 80 → Grade A (Excellent)
                              ├─ 65–79 → Grade B (Good)
                              ├─ 50–64 → Grade C (Average)
                              └─ < 50 → Grade D (Below average)
                              │
                              ▼
                           UPDATE Suppliers SET composite_score, supplier_grade
```

#### WF-08: Daily Orchestrator (The Master Pipeline) ⭐

This is the **most important workflow**. It orchestrates the entire daily intelligence cycle.

```
  Trigger: Schedule (8 AM daily) OR POST /webhook/run-pipeline
           │
           ▼
  ┌─ STEP 1: Simulate Daily Stock Depletion ──────────────────────┐
  │  Fetch all products                                            │
  │  For each product:                                             │
  │    • Skip if manually updated within 24 hours                  │
  │    • Deduct avg_daily_sales from current_stock                 │
  │    • Ensure stock doesn't go below 0                           │
  │    • Log transaction in Stock Transactions table               │
  │  UPDATE Products SET current_stock                             │
  └────────────────────────────────────────────────────────────────┘
           │
           ▼
  ┌─ STEP 2: Call WF-02 (Stockout Date Calculator) ───────────────┐
  │  Recalculate days_to_stockout for all products                 │
  └────────────────────────────────────────────────────────────────┘
           │
           ▼
  ┌─ STEP 3: Call WF-03 (Inventory Processing & Stock Alerts) ────┐
  │  Generate fresh alerts for low-stock items                     │
  └────────────────────────────────────────────────────────────────┘
           │
           ▼
  ┌─ STEP 4: Call WF-04 (Stock Risk Classification) ──────────────┐
  │  Assign HIGH/MEDIUM/LOW risk tiers                             │
  └────────────────────────────────────────────────────────────────┘
           │
           ▼
  ┌─ STEP 5: Call WF-05 (AI Reorder Intelligence) ────────────────┐
  │  Groq/Llama generates smart reorder recommendations            │
  └────────────────────────────────────────────────────────────────┘
           │
           ▼
  ┌─ STEP 6: Call WF-07 (WhatsApp Alert Sender) ──────────────────┐
  │  Send critical alerts to owner's WhatsApp                      │
  └────────────────────────────────────────────────────────────────┘
           │
           ▼
  ┌─ STEP 7: Compute & Save Daily Health Snapshot ────────────────┐
  │  health_score = weighted average of risk tiers                 │
  │  INSERT into Daily Snapshots (powers the trend chart)          │
  └────────────────────────────────────────────────────────────────┘
           │
           ▼
  ┌─ STEP 8: Log Pipeline Execution ──────────────────────────────┐
  │  INSERT into System Logs                                       │
  │  workflow_name: "WF-08 Daily Orchestrator"                     │
  │  status: "success"                                             │
  │  records_processed: N                                          │
  └────────────────────────────────────────────────────────────────┘
```

**Key Intelligence:** Products that were manually updated by the store owner within the last 24 hours are **skipped** during stock simulation. This prevents the system from overriding a real physical stock count.

### State Management Strategy

- **Global:** `AuthContext` (React Context) — provides `session`, `user`, `storeProfile`, `signIn()`, `signUp()`, `signOut()`
- **Page-level:** `useState` hooks — no Redux or Zustand. Each page fetches its own data from Supabase on mount.
- **Why no Redux?** The app is a dashboard — each page has its own data scope. No complex cross-page state sharing needed.

| `/webhook/product-sales-ingest` | POST | AddProductModal, CsvImportModal | WF-01 | Ingest a single product row |
| `/webhook/run-pipeline` | POST | Dashboard "Run Pipeline" button | WF-08 | Trigger the full daily intelligence pipeline |

### How the Proxy Works (Development)

```
  Browser (:5173)                Vite Dev Server              n8n (:5678)
  ───────────────                ──────────────                ──────────
  POST /webhook/run-pipeline ──► Vite sees /webhook/* ──► Proxy to localhost:5678
                                 (vite.config.js proxy)       n8n receives the call
```

**Why?** In development, n8n runs on `localhost:5678` and the React app on `localhost:5173`. Cross-origin requests would be blocked by CORS. The Vite proxy makes the browser think it's talking to the same origin.

**Production:** The frontend calls n8n via its ngrok URL directly (set in `VITE_N8N_BASE_URL` env var).

### Direct Supabase Access (No REST API)

For all data queries (Products, Alerts, Suppliers, etc.), the React frontend calls Supabase's JavaScript client **directly** — no intermediate REST API:

```javascript
// Example: Fetch all products
const { data, error } = await supabase.from('Products').select('*')

// Example: Update stock
await supabase.from('Products').update({ current_stock: 50 }).eq('product_id', 'MILK_01')
```

This eliminates the need for a traditional Express/Django backend for CRUD operations.

### Health Score Calculation

```
  For each product:
    LOW risk    → scores 100 points
    MEDIUM risk → scores 70 points
    HIGH risk   → scores 30 points
    OOS (stock=0) → scores 5 points

  health_score = average of all product scores (0–100 scale)
```

Example: 10 products → 3 LOW (300) + 2 MEDIUM (140) + 3 HIGH (90) + 2 OOS (10) = 540 / 10 = **54**

## 9. AI / LLM Integration — Groq + Llama 3.1

### How it Works

1. **WF-05** fetches all at-risk products (HIGH/MEDIUM/UNKNOWN risk level) and all suppliers
2. Builds a **detailed prompt** with full context:
   - Product name, stock, avg daily sales, days to stockout, reorder threshold
   - Supplier name, reliability score, price score, delivery time, categories
   - Store's safety factor (buffer multiplier)
3. Sends to **Groq API** (model: `llama-3.1-8b-instant`)
4. LLM returns **structured JSON** with recommendations:
   ```json
   [
     {
       "product_id": "MILK_01",
       "supplier_id": "SUP_DAIRY",
       "suggested_quantity": 50,
       "reason": "Critical stock: 0 units remaining with 12 units/day sales velocity. Amul Dairy Corp has 8.5/10 reliability and 2-day delivery."
     }
   ]
   ```
5. WF-05 parses and inserts into `Reorder Suggestions` table

### Why Groq over OpenAI?

| Factor | Groq | OpenAI |
|---|---|---|
| **Speed** | ~100ms inference | ~1-3 seconds |
| **Cost** | Free tier (30 req/min) | Paid ($0.15/1M tokens) |
| **Model** | Llama 3.1 8B (open-source) | GPT-4 (proprietary) |
| **Vendor Lock-in** | None — can switch to any Llama host | Locked to OpenAI API |

## 11. Realtime Architecture — Live Updates

### How Supabase Realtime Works

```
  n8n updates Products table
       │
       ▼
  PostgreSQL publishes change event
  (via ALTER PUBLICATION supabase_realtime ADD TABLE "Products")
       │
       ▼
  Supabase Realtime server broadcasts via WebSocket
       │
       ▼
  React useEffect subscription fires:
       │
       ▼
  fetchData() re-runs → setState() → UI re-renders
```

### Subscriptions in Dashboard.jsx

```javascript
const channels = [
  supabase.channel('dash-products')
    .on('postgres_changes', { event: '*', schema: 'public', table: 'Products' }, () => fetchData())
    .subscribe(),
  supabase.channel('dash-alerts')
    .on('postgres_changes', { event: '*', schema: 'public', table: 'Stock Alerts' }, () => fetchData())
    .subscribe(),
  // ... more channels
]

// Cleanup on unmount
return () => channels.forEach(c => supabase.removeChannel(c))
```

**What this means in practice:** When the pipeline finishes (n8n writes to Products, Alerts, etc.), the Dashboard updates **in real-time without page refresh**. This is the "Neural Pipeline" effect — the user sees the UI update live as the pipeline progresses.

## 13. Key Design Decisions & Trade-offs

| Decision | Why | Trade-off |
|---|---|---|
| **Direct Supabase access** (no REST API) | Eliminates an entire backend service. Faster to build. | Tightly coupled to Supabase. Row Level Security (RLS) becomes critical. |
| **n8n for business logic** (no server code) | Visual workflows are easy to modify/debug. No deployment pipeline needed. | n8n must be running for pipeline to work. Not suitable for sub-millisecond latency. |
| **Full-refresh alerts** (delete + recreate) | Guarantees no stale alerts. Simplifies logic — no "diff" needed. | Slightly less efficient than incremental updates. Fine for < 1000 products. |
| **Groq / Llama** (not OpenAI) | Free, fast, open-source model. No vendor lock-in. | Smaller model (8B params) — less "smart" than GPT-4, but sufficient for our use case. |
| **Frontend OOS override** | Clearer UX — "OOS" is more intuitive than "HIGH" when stock=0. | Risk label in DB may say "HIGH" but UI shows "OOS". Not a bug — intentional UX decision. |
| **Tailwind v4** (no config file) | Zero-config styling. `@theme` directive in CSS is cleaner. | Newer version — fewer community examples. |
