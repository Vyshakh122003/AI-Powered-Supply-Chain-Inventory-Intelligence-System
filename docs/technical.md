 Data Flow — Real-Time Path (User-Triggered)</strong></h2><ol><li>Store owner submits a product form on the React frontend.</li><li>Frontend calls WF-01 webhook via HTTPS POST, including X-StockSense-Key header for authentication.</li><li>n8n WF-01 validates the secret key, cleans and type-casts all fields, checks if product_id exists in Supabase, then upserts the record.</li><li>Supabase writes the row. Postgres NOTIFY fires. Supabase Realtime server pushes a WebSocket event to all connected dashboard subscribers filtered by store_id.</li><li>React frontend receives the WebSocket payload and updates component state — dashboard re-renders without a page refresh.</li></ol><h2><strong>2.4  Data Flow — Scheduled Path (Automatic — Daily 08:00 IST)</strong></h2><ol><li>WF-08 Schedule Trigger fires at 08:00 Asia/Kolkata (cron: 0 8 * * *).</li><li>WF-08 runs stock simulation — subtracts avg_daily_sales from current_stock (floored at 0) for every product with no manual update in last 24 hours. Logs SIMULATED transactions.</li><li>WF-08 calls Execute Workflow node → WF-02: recalculates days_to_stockout and estimated_stockout_date for every product.</li><li>WF-08 calls Execute Workflow node → WF-03: scans for products at or below threshold, creates or updates alerts using smart deduplication.</li><li>WF-08 calls Execute Workflow node → WF-04: classifies every product as OUT_OF_STOCK / HIGH / MEDIUM / LOW / UNKNOWN.</li><li>WF-08 calls Execute Workflow node → WF-05: fetches HIGH and MEDIUM risk products + all suppliers, calls Groq AI, saves suggestions.</li><li>WF-08 calls Execute Workflow node → WF-06: recalculates composite supplier scores and grades.</li><li>WF-08 calls Execute Workflow node → WF-07: sends WhatsApp digest to all store owner numbers, respecting 24-hour deduplication.</li><li>WF-08 writes one row to Daily Snapshots table — health score, counts by risk level, timestamp. Powers the Reports trend chart.</li><li>WF-08 writes one row to System Logs — workflow name, status, records processed, any errors.</li></ol><h2><strong>2.5  Multi-Tenancy Architecture</strong></h2><p>Every database table carries a store_id column (UUID) that maps to the authenticated user's ID in Supabase Auth. Row Level Security policies at the PostgreSQL level enforce complete data isolation — every SELECT, INSERT, UPDATE, and DELETE is automatically filtered to the authenticated store's data. This means even a bug in the frontend that attempts to query another store's data is silently rejected at the database level.</p><table><tr><td><p>-- RLS Policy example applied to ALL tables:</p></td></tr><tr><td><p>ALTER TABLE "Products" ENABLE ROW LEVEL SECURITY;</p></td></tr><tr><td></td></tr><tr><td><p>CREATE POLICY store_isolation ON "Products"</p></td></tr><tr><td><p>  FOR ALL USING (store_id = auth.uid());</p></td></tr><tr><td></td></tr><tr><td><p>-- Result: Every query is automatically scoped.</p></td></tr><tr><td><p>-- SELECT * FROM Products  →  only returns logged-in store's products.</p></td></tr><tr><td><p>-- No application-level filter code needed.</p></td></tr></table><table><tr><td><p><em>IMPORTANT: After enabling RLS, you must also enable Realtime for each table in Supabase Dashboard → Database → Replication → Supabase Realtime. Without this, WebSocket subscriptions silently receive nothing even though RLS is correctly configured.</em></p></td></tr></table><h1><strong>3. Each workflow is a directed acyclic graph (DAG) of nodes. Workflows communicate via Supabase as shared state — they do not call each other directly except through WF-08's Execute Workflow nodes. Mathematical Formulas — Full Derivations</strong></h1><h2><strong>5.1  Reorder Point (Threshold) Formula</strong></h2><table><tr><td><p>reorder_threshold = avg_daily_sales × delivery_time_days × safety_factor</p></td></tr></table><p><strong>Derivation from First Principles:</strong></p><p>The fundamental inventory management question is: at what stock level should a replenishment order be placed to avoid running out of stock during the supplier's lead time?</p><p>If you place an order today and the supplier delivers in 'delivery_time_days' days, your store will continue to sell during those days. The minimum stock needed at the moment of ordering is the total units sold during the waiting period:</p><table><tr><td><p>Minimum buffer needed = avg_daily_sales × delivery_time_days</p></td></tr><tr><td></td></tr><tr><td><p>Example: Milk sells 5 units/day. Supplier delivers in 3 days.</p></td></tr><tr><td><p>Minimum buffer = 5 × 3 = 15 units.</p></td></tr><tr><td></td></tr><tr><td><p>If you wait until stock hits 15 to order, you reach exactly 0 when delivery arrives.</p></td></tr><tr><td><p>No margin for error.</p></td></tr></table><p>The safety_factor adds a proportional buffer for real-world uncertainty — demand spikes (festival season, competitor closure), supplier delays (traffic, weather, stock issues), forecast inaccuracy:</p><table><tr><td><p>With safety_factor = 1.2:  threshold = 5 × 3 × 1.2 = 18 units</p></td></tr><tr><td><p>With safety_factor = 1.5:  threshold = 5 × 3 × 1.5 = 22 units</p></td></tr><tr><td><p>With safety_factor = 1.0:  threshold = 5 × 3 × 1.0 = 15 units (no buffer)</p></td></tr></table><p><strong>Academic Basis:</strong></p><p>This is the classical Reorder Point (ROP) formula from inventory management: ROP = (Average Demand Rate × Lead Time) + Safety Stock. The safety_factor parameterisation simplifies Safety Stock from requiring the standard deviation of demand (unavailable for small stores without historical POS data) to a proportional buffer, making it practical for SME deployment. Reference: Silver, Pyke, Thomas — Inventory and Production Management in Supply Chains, CRC Press.</p><table><thead><tr><th><p><strong>Safety Factor</strong></p></th><th><p><strong>Mode</strong></p></th><th><p><strong>Buffer</strong></p></th><th><p><strong>Best Used For</strong></p></th></tr></thead><tbody><tr><td><p>1.0</p></td><td><p>Aggressive</p></td><td><p>0% buffer</p></td><td><p>Very reliable suppliers, stable demand, limited storage space</p></td></tr><tr><td><p>1.2</p></td><td><p>Standard (Default)</p></td><td><p>20% buffer</p></td><td><p>Most kirana products under typical Indian supply conditions</p></td></tr><tr><td><p>1.5</p></td><td><p>Conservative</p></td><td><p>50% buffer</p></td><td><p>Perishables, unreliable suppliers, high-demand products</p></td></tr></tbody></table><h2><strong>5.2  Days To Stockout</strong></h2><table><tr><td><p>days_to_stockout = Math.floor(current_stock / avg_daily_sales)</p></td></tr><tr><td></td></tr><tr><td><p>Edge cases:</p></td></tr><tr><td><p>  avg_daily_sales = 0 or null  →  days_to_stockout = 999   (no sales data, treated safe)</p></td></tr><tr><td><p>  current_stock = 0            →  days_to_stockout = 0     (OUT_OF_STOCK)</p></td></tr><tr><td><p>  Result is always integer     →  Math.floor() used        (cannot have 0.7 days)</p></td></tr></table><p>This is the foundational formula. Every risk classification and every WhatsApp alert derives from this single number. Its accuracy depends entirely on avg_daily_sales being current — which is why WF-08 recalculates it from real transaction history as data accumulates.</p><h2><strong>5.3  Store Health Score</strong></h2><table><tr><td><p>health_score = (</p></td></tr><tr><td><p>  (low_count    × 1.0) +</p></td></tr><tr><td><p>  (medium_count × 0.5) +</p></td></tr><tr><td><p>  (high_count   × 0.0) +</p></td></tr><tr><td><p>  (oos_count    × 0.0)</p></td></tr><tr><td><p>) / total_products × 100</p></td></tr></table><p><strong>Weight Rationale:</strong></p><ul><li>LOW (1.0): Healthy product. Full contribution. No concern.</li><li>MEDIUM (0.5): Warning state. Half contribution. Needs attention this week but not today.</li><li>HIGH (0.0): Crisis state. Zero contribution. A product about to run out provides no inventory health value. Its existence represents active revenue risk.</li><li>OUT_OF_STOCK (0.0): Already failed. Zero contribution. Represents actual lost sales.</li></ul><p><strong>Interpretation:</strong></p><table><thead><tr><th><p><strong>Score</strong></p></th><th><p><strong>Status</strong></p></th><th><p><strong>Dashboard Color</strong></p></th><th><p><strong>Recommended Action</strong></p></th></tr></thead><tbody><tr><td><p>85–100</p></td><td><p>Excellent</p></td><td><p>Green</p></td><td><p>Well-stocked. Monitor normally.</p></td></tr><tr><td><p>65–84</p></td><td><p>Good</p></td><td><p>Light Green</p></td><td><p>Minor attention needed for MEDIUM items.</p></td></tr><tr><td><p>45–64</p></td><td><p>Warning</p></td><td><p>Orange</p></td><td><p>Multiple products at risk. Review alerts today.</p></td></tr><tr><td><p>Below 45</p></td><td><p>Critical</p></td><td><p>Red</p></td><td><p>Significant stockout risk. Immediate action required.</p></td></tr></tbody></table><p><strong>Academic Basis:</strong></p><p>Weighted Scoring Model — standard technique in performance management. Same logic used in academic GPA calculation, balanced scorecard methodology, and KPI dashboards across industries. The non-linear weight structure (1.0/0.5/0.0 rather than 1.0/0.67/0.33) reflects the non-linear business impact: a HIGH risk product is not just 'a bit worse' than MEDIUM — it is an imminent revenue loss event.</p><h2><strong>5.4  Supplier Composite Score</strong></h2><table><tr><td><p>// Step 1: Min-Max Normalization</p></td></tr><tr><td><p>delivery_speed_score = 1 − ((days − min_days) / (max_days − min_days))</p></td></tr><tr><td></td></tr><tr><td><p>// Step 2: Weighted Sum Model</p></td></tr><tr><td><p>composite_score = (</p></td></tr><tr><td><p>  reliability_score    × 0.40 +</p></td></tr><tr><td><p>  price_score          × 0.35 +</p></td></tr><tr><td><p>  delivery_speed_score × 0.25</p></td></tr><tr><td><p>) × 100</p></td></tr></table><p><strong>Weight Selection Rationale (SME Context):</strong></p><table><thead><tr><th><p><strong>Criterion</strong></p></th><th><p><strong>Weight</strong></p></th><th><p><strong>Justification</strong></p></th></tr></thead><tbody><tr><td><p>Reliability</p></td><td><p>40%</p></td><td><p>For a kirana with no warehouse buffer, a supplier who fails to deliver once causes an immediate stockout. Reliability is non-negotiable and therefore carries highest weight.</p></td></tr><tr><td><p>Price</p></td><td><p>35%</p></td><td><p>A small store operates on 5–15% margins. A 5% improvement in purchase price can represent the entire margin on a product. Price is second only to reliability.</p></td></tr><tr><td><p>Delivery Speed</p></td><td><p>25%</p></td><td><p>Faster delivery is convenient but a supplier who delivers in 2 days vs. 3 days matters far less than whether they deliver reliably at all. Reliability and price are already 0–1 decimal scores. Adding these directly (3 + 0.8 + 0.7) is mathematically invalid — you are adding units that have no common scale. Min-Max Normalization maps all delivery times to the same 0–1 space so the weighted sum is dimensionally consistent. This is a standard technique in data science and multi-criteria decision analysis literature (TOPSIS, WSM).</p><p><strong>Grade Boundaries:</strong></p><table><thead><tr><th><p><strong>Grade</strong></p></th><th><p><strong>Score</strong></p></th><th><p><strong>Meaning</strong></p></th><th><p><strong>Recommended Action</strong></p></th></tr></thead><tbody><tr><td><p>A</p></td><td><p>80–100</p></td><td><p>Excellent supplier</p></td><td><p>Preferred.
